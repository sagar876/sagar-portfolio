In an offline-first application the network is an optimisation, not a requirement. The interface reads from and writes to a local database, and a background process keeps that database in step with the server. The user never waits on a request to see their own changes.

## The local database is the source of truth

IndexedDB is the browser's transactional, asynchronous key-value store. It can hold far more data than `localStorage` and does not block the main thread. The raw API is event-based and verbose, so most applications use a thin wrapper that returns promises.

Design stores around how the interface reads data, not around the server's tables. Add indexes for every query the UI makes, because IndexedDB cannot filter efficiently without them.

## Writes go through a queue

Every change the user makes is written to two places in a single transaction: the record itself and an outbox entry describing the change.

```ts
type OutboxEntry = {
  id: string;
  entity: "task";
  entityId: string;
  operation: "create" | "update" | "delete";
  payload: unknown;
  createdAt: number;
  attempts: number;
};
```

A sync worker reads the outbox in order, sends each change to the server and removes it on success. Because the record and the outbox entry are written together, a crash can never leave a change that was saved but not queued.

## Syncing when the network returns

Listen for the `online` event, but do not trust it on its own; it only says a network interface exists. Treat a successful request as the real signal, and retry failures with exponential backoff and a cap.

Pull changes from the server using a cursor, such as a last-synced timestamp or version, so each sync only fetches what changed.

## Conflicts

Conflicts happen when the same record changes locally and on the server before they sync. Choose a strategy per entity rather than one for the whole app:

- **Last write wins** — simple, and fine for data only one person edits
- **Field-level merge** — combine changes to different fields of the same record
- **Ask the user** — for data where silently losing an edit is unacceptable

Whatever the strategy, show sync state in the interface. People trust offline features when they can see what is saved locally, what is syncing and what failed.

## Testing checklist

1. Make changes offline, reload the page, and confirm they are still there.
2. Go back online and confirm the outbox drains in order.
3. Edit the same record on two devices and check the conflict outcome.
4. Fill storage close to the quota and check the error handling.
